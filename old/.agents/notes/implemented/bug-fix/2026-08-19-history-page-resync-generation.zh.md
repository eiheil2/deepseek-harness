# Agent Note：历史分页跟随连接代次

Status: implemented

[English](2026-08-19-history-page-resync-generation.md) | 中文

## 问题

重连 resync 替换 Session 窗口时，旧页请求可能仍在进行。Resync 会使尾页 open 和 gap repair 失效，却没有把 `loadOlder()` 纳入同一代次规则。旧响应到达后，会拿自己的页面与重建窗口的新 `baseSeq` 比较，在不连续时清除 `hasMore`，并结算共享加载位。因此，新分页请求可能一直被旧请求阻塞到其结算，或者自己的加载状态被旧请求的结算清除。

## 决策

每个旧页请求捕获当前 open 代次与 `baseSeq`。只有该代次仍为当前代次、Session 仍处于 open 状态且窗口仍从捕获的序列开始时，它才可以写入。Resync 在打开重建窗口前释放上一代的加载位。陈旧请求的 catch 和 finally 路径也检查代次所有权，因此既不会报告已经失效的传输错误，也不会结算更新分页请求的状态。

## 考虑过的替代方案

在传输层中止旧 RPC 可以节省工作，但分页共用通用请求路径，单靠取消也不能证明迟到响应不会写入。让 resync 等待分页完成会保留陈旧请求，既延迟恢复，也仍然让新窗口依赖旧传输状态。由代次控制的提交门禁局限在 Session 状态内，覆盖成功、失败和清理路径，而且不需要修改协议。

## 验证与边界

Session 分页测试暂停一个旧页响应，resync 到新的尾页，发起新的旧页请求，再先解析陈旧响应。陈旧页面不能改变重建后的节点或 `hasMore`，其完成也会让新请求保持加载中，直到新请求安装自己的连续页面。

该规则只在连接代次或窗口头发生变化时使分页读取失效。实时尾部追加不会改变 `baseSeq`，所以旧页请求进行时仍可继续追加。

## 结果

重连不再允许过时的历史响应破坏当前窗口或分页控件状态。同一代次内与窗口头替换发生竞态的页面响应会被丢弃，而不会合并进不同范围；用户可以从新窗口头重新请求该页面。
