# Agent Note：隔离重启前后的连接循环生命周期

Status: implemented

[English](2026-08-18-connection-restart-lifetime.md) | 中文

## 问题

`ConnectionController` 的每次 `start()` 共用同一个可变 `running` 标记。如果旧循环正在等待重连退避时执行 `stop()` 并立即 `start()`，旧循环恢复后会读到新一次启动写入的 `running` 值。它随后会在新循环旁再打开一个流 generation，并可能覆盖 `current` 中保存的 controller，使下一次 `stop()` 无法中止其中一代。

## 决策

每次有效的 `start()` 都会为该次循环生命周期创建一个私有中止信号。`stop()` 同时中止该生命周期及其当前流 generation。循环捕获自己的生命周期信号，并在就绪、流故障、状态回调和退避等待后检查该信号，因此后续 start 无法让已停止循环重新存活。重连退避监听同一信号，并在该生命周期停止时解除等待。

既有 `running` 标记只作为同一活动生命周期内重复调用 `start()` 时的同步幂等保护，不再授权异步流程继续运行。

## 验证与边界

连接生命周期测试在固定退避延迟下，于首次 `reconnecting` 状态回调中同步停止并重启。测试证明只有初始连接和一次重启连接进入就绪状态，而且旧退避本应结束后仍恰好只有一条 mux 流处于活动状态。既有用例继续覆盖普通重连、显式停止、就绪期间停止和重复启动。

该决策隔离同一个 `ConnectionController` 内的循环所有权；它不会串行化相互独立的 mux 与 host 流，也不增加跨流顺序保证。

## 考虑过的替代方案

**只使用单调递增的 epoch 而不取消。** epoch 检查能阻止旧循环打开另一个 generation，但它的定时器以及未来由生命周期持有的等待仍会持续到自然结束。中止信号既标识所有者，也能释放可取消工作。

**让重启等待先前循环完成。** 把 `start()` 或 `stop()` 改成异步 API 会把生命周期协调扩散到所有调用方。捕获生命周期信号可以保留既有同步控制 API。

**继续共用 `running` 标记，只更谨慎地清理 `current`。** 在一次等待结束后，任何赋值顺序都无法让共享 Boolean 区分已停止的旧循环和新启动的循环。缺失的信息是生命周期身份。

## 影响

快速 stop/start 后仍只有一个连接循环、一条 mux 流和一条 host 流。退避期间停止会立即释放延迟，后续启动则独立进行。controller 在每个活动循环生命周期内会额外持有一个 `AbortController`。
